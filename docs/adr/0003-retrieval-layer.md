# A11 检索层：用数据推翻的两个直觉

> 日期：2026-11-15　环境：bge-m3 (CUDA) + DeepSeek + pgvector
> 复现：`uv run python tests/eval/run_eval.py --label <标签> [--keyword]`
>
> **后续（2026-11-17）**：本文的"中文分词不可用"与"reranker 未实现"
> 已在 ADR 0009 解决（jieba 预分词 + 内置 FTS、`LocalBGEReranker`），
> 生产链路也已接入 `RetrievalGraph`。本文保留为"当时的数据与结论"，
> 不再作为现状说明。

## 1. 评估基线（30 条查询，3 份制度文档，37 chunk）

| 指标 | 纯向量检索 |
|---|---|
| Recall@10 | 100.0% |
| MRR@10 | 0.964 |
| Hit@10 | 100.0% |
| 误报率（unanswerable） | 100.0% |
| 平均延迟 | 6.3ms |

Recall/Hit 满分，**但这个满分是"语料太小"造成的**，不能推广（见第 3 节）。

## 2. 结论一：距离阈值做不了拒答（数据证明）

A11 最想当然的方案是"距离太远就拒答"。30 条查询的实测数据否决了它：

| | top1 余弦距离 |
|---|---|
| 有答案的**最大** | 0.527（"京沪广深算几线城市"） |
| 无答案的**最小** | 0.437（"食堂几点开饭"） |

**区间重叠**（0.437 < 0.527）。任何阈值都会误判：

- 设 0.45 → 误杀"京沪广深算几线城市"（它其实有答案，只是"京沪广深"
  这个缩写与"北京、上海、广州、深圳"的 embedding 距离偏远）；
- 设 0.55 → 放过"食堂几点开饭"（它其实无答案，但"公司制度"语境
  与薪酬福利文档语义相近）。

根因：**embedding 相似度衡量语义相近，不衡量"能否回答"**。
两个指标在概念上就不同，不能互相替代。

### 正确做法：生成前判断"材料能否回答"

用一次独立 LLM 调用判断（`build_answerability_prompt`）。实测 6/6 正确：

| 查询 | 应拒答 | 判断结果 |
|---|---|---|
| 一线城市住宿上限 | 否 | ✓ 能回答 |
| 公司股票期权怎么兑现 | 是 | ✓ 不能回答 |
| 食堂几点开饭 | 是 | ✓ 不能回答 |
| 陪产假有多少天 | 否 | ✓ 能回答 |
| 京沪广深算几线城市 | 否 | ✓ 能回答（**距离 0.527 但能答**） |
| 员工能带宠物上班吗 | 是 | ✓ 不能回答（编造的无关问题） |

代价：每次问答多一次 LLM 调用（约 500~1500ms）。可按场景开关。

### 一个必须分开的概念（踩过的坑）

最初我把"答案是否有材料支撑"当成拒答依据，结果：

```
问"食堂几点开饭" → 模型生成"根据现有资料无法回答"
→ "答案是否有支撑"检查看到"没有事实性陈述" → 通过
→ 系统记为"正常回答"，误报率恒为 100%
```

两个判断**语义不同**，不能混用：

- `answerability`（生成前）：材料能否回答这个问题 → **决定是否拒答**；
- `support`（生成后）：答案中的事实是否都有材料依据 → **拦住幻觉**。

代码上它们是两个提示词（`build_answerability_prompt` /
`build_self_check_prompt`），共用 `SelfCheckResult` 结构但语义由调用方保证。

## 3. 结论二：混合检索在 37-chunk 语料上零收益、100 倍延迟

| 配置 | Recall | MRR | 延迟 |
|---|---|---|---|
| 纯向量 | 100% | 0.955 | 6ms |
| + 关键词（RRF） | 100% | 0.955 | 655ms |

延迟暴涨的**直接原因**不是数据库（关键词 SQL 实测 0.34ms），
而是关键词提取太粗暴（12+ 个 token 全进 `to_tsquery` 的 OR 链）。
改进到 8 个后延迟没降——说明还有别的一次性开销（首次调用分摊）。

**但根本原因是另一个**：`search_keyword` 用的是 `simple` 分词器，
它**不认中文**（A10 已记录这个待办）。所以关键词检索在这个语料上
命中数经常是 0——融合时等于只有向量一路，指标自然完全不变。

这不是"混合检索没用"，是"混合检索的稀疏路当前不可用"。
要验证它的价值，必须先解决中文分词（zhparser / pg_bigm / 应用侧分词）。

### 为什么不给混合检索"编"一个正面结论

可以只挑对关键词敏感的查询（"内线 8888"），做出"混合检索提升 X%"的
数字。但那份数据不可复现于真实分布，属于自欺。

诚实的记录是：**当前无法验证，因为前置条件（中文分词）不满足**。

## 4. 方法论：metric ceiling 与语料规模

黄金集 30 条查询里，**连"keyword_sensitive"类（内线 8888、五险一金、
发票抬头）纯向量也 100% 命中**。bge-m3 的中文能力超出预期。

这意味着：**37-chunk 语料无法区分检索策略的优劣**——所有策略都拿满分。

要真正比较，语料必须满足：
- 规模足够大（同一主题有多个相似文档，迫使检索器做选择）；
- 包含"近似但错误"的干扰项（如两份制度都提到住宿，但标准不同）。

本步骤没有造这样的语料，原因：
- 造一份有说服力的大语料（几千 chunk + 人工标注）工作量远超当前步骤；
- A15 才是"评估与验收"阶段，届时应该用**真实业务文档**建黄金集，
  而不是现在这 3 份手写示例。

**A11 的验收标准（每加节点做对比）已经满足：流程跑通、指标可比、
结论可复现。** 语料规模不足是 A15 要解决的问题，记在这里避免误以为
"检索已经调优完毕"。

## 6. 检索图的形状选择

用**顺序调用**而不是 LangGraph 的 `ainvoke`：

当前图是线性的（有开关但无条件跳转），顺序调用更易读、更易测、
能精确记录每节点耗时。LangGraph 的价值在"条件分支与循环"时体现
（自省不通过 → 重新检索 → 再自省）。等真需要循环时再改成
`StateGraph`，不为用框架而用框架。

依赖已装（`langgraph`），改造只涉及 `RetrievalGraph.run`。

## 7. 遗留

1. **中文分词**：`search_keyword` 的 `simple` 分词器不认中文。
   选项：`zhparser`（需编译）、`pg_bigm`（模糊匹配）、应用侧 jieba 预分词。
2. **reranker 未实现**：`RerankerProvider` 接口与 `NoOpReranker` 占位已有，
   真实实现（bge-reranker）需下载模型。
3. **语料规模**：见第 4 节，留给 A15。
4. **评估脚本的 mypy**：`tests/eval/` 不在严格检查范围（脚本类代码），
   已加注释说明但未强制类型。
