## 二、性能与容量（A15 实测）

### 检索路径压测

环境：本机 PG（pool_size=10, max_overflow=10 → 上限 20 连接），37 chunk 语料。

| 并发 | QPS | P50 (ms) | P95 (ms) | P99 (ms) | 成功率 |
|---|---|---|---|---|---|
| 5 | 341.0 | 13.6 | 14.7 | 15.2 | 100% |
| 10 | **344.4** | 26.9 | 28.6 | 56.5 | 100% |
| 20 | 320.6 | 55.7 | 71.1 | 325.2 | 100% |
| 40 | 302.5 | 112.8 | 388.2 | 441.7 | 100% |
| 80 | 300.4 | 230.1 | 546.2 | 673.6 | 100% |

**饱和点：并发 10，QPS ≈ 344**。之后 QPS 不再增长（320 → 302 → 300），
而 P99 从 56ms 涨到 673ms —— 典型的高并发排队而非吞吐提升。

**关键结论：瓶颈不在连接池**。80 并发、池上限 20，却零错误，
说明每个请求持连接时间极短（释放快），池不是瓶颈；
瓶颈是单机 CPU（37 chunk 的全表扫描占比高，索引在小数据量下不被选用，见 ADR 0002）。

**压测后连接池完全恢复**：`active=1, idle=9, idle_in_transaction=0,
longest_idle_tx=0s` —— 无连接泄漏、无残留事务。

### 延迟分层（来自 A11/A12 实测）

| 环节 | 耗时 | 备注 |
|---|---|---|
| 向量检索 | 4~35ms | 首次含模型加载 |
| 检索（含重建索引） | 6.3ms 基线 | 37 chunk |
| 引用组装 | <1ms | 纯计算 |
| LLM 调用 | 3~5s | 主要成本与延迟来源 |
| bge-m3 embedding | 247ms / 7 chunk | GPU，含首次加载 23s |

**端到端问答的延迟由 LLM 主导**，检索层不是瓶颈——优化重点应在
缓存与 prompt 长度，而非索引参数。

### 指标满分的诚实解读

Recall/Hit 100% **不代表检索已调优完毕**：语料只有 37 个 chunk，
所有策略（含纯向量、混合、结构化）都拿满分——这是 metric ceiling，
无法区分优劣。真正需要更大语料 + "近似但错误"的干扰项，
留给用真实业务文档建库时重做（ADR 0003 已记录）。

### 对账本身经过破坏性验证

| 注入的错误 | 是否被检出 |
|---|---|
| 删掉一条向量 | ✓ 缺失 1 个 |
| chunk.tenant_id 改成别的租户 | ✓ 不一致 1 条 |
| 文档 chunk_count 写成 999 | ✓ 不一致 |
| 插入指向不存在 chunk 的向量 | ✓ 孤儿 1 条 |
| 重复 chunk_index（临时删约束） | ✓ 重复 1 组 |

**这一步抓到一个真实 bug**：评估库的 3 个文档 `chunk_count=0` 但实际有
11/16/10 个 chunk —— 评估脚本建库绕过了状态机与计数更新。
已修（建文档时直接写 ready + 正确计数）。

### 对账逻辑本身也有两个 bug（都被破坏性验证抓出）

1. **跨租户检查自己把证据过滤掉**：原版用 `c.tenant_id = :tid` 过滤，
   而注入的错误正好让该行不满足此条件 → 漏报。改为按父表
   （`d.tenant_id`）过滤。
2. **chunk_count 检查有盲区**：原版查 `status='ready'`，漏掉状态不正确的
   文档；改成 `chunk_count > 0` 后仍漏（评估库的记录值本来就是 0）。
   最终改为**从 chunk 侧聚合**，无论记录值是 0 还是错值都能抓到。

## 九、结论

**后端第一阶段（A2–A15）功能完整、测试充分、数据可复现。**

核心链路（上传 → 解析 → 切分 → 向量化 → 检索 → 引用）在真实环境下
端到端跑通，且每一步都用真实数据验证过（不是 mock）。

最值得记的三条经验：

1. **"配好了却没生效"是最危险的故障形态**。HNSW 部分索引、
   `random_page_cost`、JOIN 写法，三者都让索引"看起来建好了"却
   完全不被使用——不报错，只是慢 30~140 倍。只有 EXPLAIN 能发现。
2. **检查逻辑可能自己把证据过滤掉**。跨租户对账的 WHERE 条件
   正好排除了注入的错误行。所以对账必须做**破坏性验证**
   （注入错误 → 确认检出），否则它可能永远是"通过"。
3. **满分的指标先怀疑测试集**。37 chunk 上所有策略都 100%，
   这不是"检索完美"，是"测不出来"。

下一步进入 Phase B（React 用户前端）与 Phase C（管理端），
前者会先接 A4/A6/A11/A12 的接口，届时上述"未接线"项会集中补齐。
